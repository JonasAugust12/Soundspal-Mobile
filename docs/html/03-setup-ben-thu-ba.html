Setup bên thứ ba & Auto Deploy

Hướng dẫn thao tác thật, từng bước bấm, để dựng lại toàn bộ dịch vụ bên ngoài mà app phụ thuộc: Google Cloud, Firebase FCM, Google Sign-In, PayOS, Socket.IO, EAS Build, Google Play Console và Fastlane. Kèm cách xử lý những lỗi hay gặp nhất ở mỗi phần.

Đọc mục 1 trước khi làm bất cứ mục nào khác Gần như mọi lỗi tích hợp trong dự án này đều bắt nguồn từ hai định danh phải khớp nhau ở nhiều nơi: package name và OAuth client ID.

2. File .env — 7 biến

Chép .env.example thành .env rồi điền. Không có giá trị mặc định trong source — thiếu biến thì app vẫn build nhưng không gọi được backend.

EXPO_PUBLIC_AUTH_REFRESH_URL apiClient.ts (interceptor 401) URL tuyệt đối, không phải path. Hiện đang trỏ domain cũ talentlink.io.vn — kiểm tra lại với backend

Hiểu đúng tiền tố EXPO_PUBLIC_ Tiền tố này khiến giá trị bị nhúng thẳng vào file .apk/.ipa. Bất kỳ ai giải nén file cài đặt đều đọc được. Nó dùng để tách môi trường (dev/staging/prod), không phải kho bí mật. Tuyệt đối không đặt mật khẩu, client_secret, hay private key vào đây.
Sửa .env xong phải xoá cache Expo đọc .env tại thời điểm bundle. Chạy npm run start:clear (tức expo start -c), nếu không giá trị cũ vẫn được dùng.

3. Firebase Cloud Messaging (Push notification)

3.1. Tạo project và đăng ký app Android

  1. Tạo Firebase project Vào console.firebase.google.com → Add project. Đặt tên (dự án hiện dùng talentlink-22clc). Google Analytics có thể tắt — FCM không cần.
  2. Thêm ứng dụng Android Trong project → biểu tượng Android. Điền Android package name = com.jonasaugust12.talent_link chính xác từng ký tự như trong app.json. Sai một chữ là FCM không bao giờ giao được tin.
  3. Tải google-services.json Đặt vào thư mục gốc repo (cùng cấp package.json). app.json đã trỏ tới nó qua "googleServicesFile": "./google-services.json".
    File này nằm trong .gitignore Nó không được commit. Vì vậy CI phải tự ghi lại từ secret trước khi build — xem mục 8.3. Đồng thời .easignore cố tình không liệt kê file này, để EAS đóng gói kèm khi build.
  4. Bật Cloud Messaging API Firebase Console → Project settings → Cloud Messaging. Nếu thấy "Firebase Cloud Messaging API (V1)" đang Disabled, bấm bật (nó mở link sang Google Cloud Console).
  5. Cấp credential cho backend gửi push Project settings → Service accounts → Generate new private key. File JSON tải về đưa cho backend. Backend dùng nó với FCM HTTP v1 API để đẩy thông báo. Đây là khoá bí mật — không commit, không đặt vào .env của app.

3.3. Backend cần gửi payload như thế nào

App suy ra màn hình đích từ khối data (resolvePushRoute.ts). Quy tắc: ưu tiên type + id, còn route/path chỉ là phương án cuối.

data.type Cần kèm App mở màn
new_application job_id /(jobs)/applicants?id=…
application_status_changed — /(jobs)/my-applications
new_message conversation_id /(messages)/detailMessage?conversationId=…
(không có type) conversationId Vẫn mở được phòng chat
Hai backend đặt tên khác nhau — app đã xử lý job-post-service gửi snake_case (job_id, conversation_id), còn messaging-service gửi camelCase (conversationId) và không gửi type. Hàm pick() trong resolvePushRoute.ts thử lần lượt cả hai kiểu.

Cũng lưu ý: messaging-service đính sẵn route: "/(messages)/<id>" nhưng route đó không tồn tại trong app — nên code cố tình ưu tiên suy từ type+id trước.

3.4. Kiểm tra push có chạy không

  1. Lấy FCM token của máy test Đăng nhập app rồi xem log — useDevicePayload ghi token ra console. Hoặc hỏi backend token đã lưu cho device_id đó.
  2. Gửi thử từ Firebase Console Engage → Messaging → New campaign → Notifications → Send test message → dán token. Nếu banner hiện: FCM + quyền OK.
  3. Test điều hướng khi bấm Gửi bằng API v1 kèm khối data (Console không gửi được data tuỳ ý), rồi bấm vào thông báo, kiểm tra app mở đúng màn.
  4. Test push tin nhắn — nhớ tắt màn hình Messaging-service chỉ push cho người offline. App chủ động ngắt socket khi xuống nền. Nên phải thực sự đưa app xuống nền rồi mới nhờ người khác nhắn.

4.1. Tạo Google Cloud project & OAuth consent screen

  1. Tạo project console.cloud.google.com → Select a project → New project. (Dự án đang dùng talent-link-480717.)
  2. Cấu hình OAuth consent screen APIs & Services → OAuth consent screen. Chọn External. Điền tên ứng dụng, email hỗ trợ, email liên hệ nhà phát triển. Scope chỉ cần email, profile, openid.

    Khi ở trạng thái Testing, chỉ tài khoản trong danh sách Test users đăng nhập được (tối đa 100). Muốn mở cho tất cả thì bấm Publish app. Với 3 scope cơ bản trên thì không cần Google thẩm định.

4.2. Tạo hai OAuth client — và hiểu vì sao cần cả hai

Điểm gây bối rối nhất Bạn phải tạo 2 client, nhưng trong code chỉ dùng 1:
  • Android client — không xuất hiện ở đâu trong code. Nó tồn tại để Google xác minh rằng app gọi tới đúng là app của bạn, dựa vào chữ ký SHA-1.
  • Web client — đây mới là cái đưa vào EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID, và backend phải giữ đúng client_secret của chính client này. Lệch nhau là backend trả 401 oauth_failed.
  1. Lấy chữ ký SHA-1 Debug (máy dev): 
    keytool -list -v -keystore ~/.android/debug.keystore \
        -alias androiddebugkey -storepass android -keypass android
    Release qua EAS — EAS quản lý keystore giúp bạn: 
    eas credentials
# chọn: Android → production → Keystore → xem SHA-1 fingerprint
    Bản do Google Play ký (khi bật Play App Signing): Play Console → Setup → App integrity → App signing → chép SHA-1 ở mục App signing key certificate.
    Có tới 3 SHA-1 khác nhau (debug / upload key của EAS / key Google Play ký). Muốn đăng nhập Google chạy được ở cả bản dev lẫn bản trên Play thì phải thêm hết cả ba vào Android OAuth client.
  2. Tạo Android OAuth client APIs & Services → Credentials → Create credentials → OAuth client ID → Android. Package name com.jonasaugust12.talent_link, dán SHA-1. Lặp lại cho từng SHA-1.
  3. Tạo Web OAuth client Cũng ở Create credentials → OAuth client ID → chọn Web application. Chép Client ID vào .env, và đưa Client secret cho backend. 
    EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID=1234567890-xxxxxxxx.apps.googleusercontent.com
  4. Kiểm tra cấu hình phía app Đã viết sẵn trong useGoogleSignIn.ts, không cần sửa: 
    GoogleSignin.configure({
    webClientId: process.env.EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID,
    offlineAccess: true,            // bắt buộc — không có thì Google không trả serverAuthCode
    forceCodeForRefreshToken: true, // buộc trả code mới mỗi lần
});
  5. Build lại development build Google Sign-In là native module — Expo Go không chạy được. Chạy npx expo prebuild --clean rồi npm run android.

4.3. Bảng lỗi thường gặp

Lỗi Nguyên nhân thật sự Cách sửa

4.4. Người dùng Google lần đầu — luồng 2 bước

Backend trả is_registered để phân biệt. Nếu false, nó gửi kèm registration_token, app chuyển sang màn /(auth)/complete-oauth-profile để người dùng chọn role (producer/singer/venue) và username, rồi gọi POST /auth/complete-oauth mới nhận được token thật.

5. PayOS (Thanh toán Premium)

PayOS là cổng thanh toán Việt Nam, dùng VietQR. Điểm mấu chốt của tích hợp này: app không hề xử lý tiền. Nó chỉ xin backend một checkout_url, mở URL đó bằng trình duyệt hệ thống, rồi chờ người dùng quay lại app qua deep link.

5.1. Đăng ký & lấy khoá

  1. Tạo tài khoản kênh thanh toán Đăng ký tại my.payos.vn, hoàn tất xác minh doanh nghiệp/cá nhân và liên kết tài khoản ngân hàng nhận tiền.
  2. Tạo kênh thanh toán và lấy 3 khoá Trong dashboard, mỗi kênh có Client ID, API Key, Checksum Key.
    Cả ba khoá này thuộc về backend. Tuyệt đối không đưa vào app — EXPO_PUBLIC_* ai cũng đọc được, và Checksum Key là thứ dùng để xác thực webhook. Lộ nó nghĩa là bất kỳ ai cũng giả được "đã thanh toán".
  3. Đăng ký webhook URL Trong dashboard PayOS, khai báo endpoint webhook của backend (vd https://api.soundspal.com/api/v1/payments/webhook). PayOS gọi vào đây khi giao dịch đổi trạng thái. Đây mới là nguồn sự thật, không phải redirect URL — người dùng có thể đóng trình duyệt trước khi bị chuyển hướng.

5.2. Deep link — cách người dùng quay lại app

app.json khai báo "scheme": "soundspal". Ở PremiumScreen.tsx: 

const paymentReturnUrl = useMemo(
    () => ExpoLinking.createURL('/(payments)/premium'),
    []
);
// → "soundspal:///(payments)/premium" trên bản build thật

createCheckout({
    redirect_url: paymentReturnUrl,
    cancel_url:   `${paymentReturnUrl}?cancel=1`,
    ...
});
PayOS chỉ nhận URL http/https ở phần cấu hình dashboard Nếu PayOS từ chối scheme soundspal://, cách chuẩn là dùng trang trung gian: đặt redirect_url là một trang web của bạn (https://soundspal.com/payment-return), trang đó nhận orderCode + status rồi tự chuyển tiếp sang soundspal://…. Cách này cũng xử lý được trường hợp người dùng thanh toán trên máy khác.

5.3. Luồng thanh toán đầy đủ

  1. Người dùng chọn gói Bảng giá nằm cứng trong code (features/payments/domain/constants/payment.ts): tháng 49 000 ₫ / năm 490 000 ₫ (= 10× giá tháng, tặng 2 tháng). Mặc định chọn gói năm.
    Bảng giá này phải khớp bảng giá server. Payment-service re-validate amount theo billing_period và từ chối nếu lệch — chống việc sửa giá từ client.
  2. App gọi tạo phiên thanh toán POST /payments/checkout với body: 
    {
    purpose: 'ACCOUNT_UPGRADE',
    amount: 490000,
    billing_period: 'yearly',
    description: 'Soundspal Premium 1Y',   // ≤25 ký tự ASCII không dấu!
    reference_id: user.id,
    redirect_url: 'soundspal:///(payments)/premium',
    cancel_url:   'soundspal:///(payments)/premium?cancel=1'
}
    description phải ≤ 25 ký tự ASCII không dấu. PayOS dùng chuỗi này làm nội dung chuyển khoản VietQR. Dài hơn hoặc có dấu tiếng Việt → CreatePaymentLink thất bại.
  3. Mở PayOS Backend trả checkout_url, app gọi Linking.openURL(checkoutUrl) — mở trình duyệt ngoài, không phải WebView.
  4. Người dùng quét VietQR và chuyển khoản Ngân hàng xử lý. PayOS phát hiện tiền về.
  5. PayOS gọi webhook backend (đường chính) Backend xác minh chữ ký bằng Checksum Key, rồi set is_premium = true và premium_expired_at = now + 30/365 ngày trên user-service.
  6. PayOS chuyển hướng người dùng về app (đường phụ) Deep link mang theo orderCode và status. parsePayOSReturnUrl() đọc chúng. Hàm này xử lý khá nhiều biến thể: status / payment_status / paymentStatus, quy ước code=00 nghĩa là đã trả tiền, và cancel=1 hoặc cancel=true nghĩa là huỷ.
  7. App poll trạng thái GET /payments/status/{orderCode}, mỗi 2 giây, tối đa 10 lần (~20 giây). Hết hạn mức mà vẫn pending → hiện màn "đang xử lý" (webhook có thể tới muộn hơn). Riêng lỗi 404 được retry tới 8 lần vì giao dịch có khi chưa kịp ghi vào DB.
  8. Thành công → làm mới quyền lợi Invalidate userKeys.all + paymentKeys.all để /users/me trả về cờ premium mới.
Cứu cánh khi không lấy được orderCode Nếu người dùng quay lại app mà deep link không mang orderCode (đóng trình duyệt, mở lại app bằng tay…), resolvePaymentOrderCodeFromHistory() gọi GET /payments/history?limit=10 và lấy order_code mới nhất. PremiumScreen cũng lắng nghe AppState để tự refetch trạng thái mỗi khi app quay lại foreground.

5.4. Trạng thái Premium — đọc thế nào cho đúng

// shared/domain/utils/premium.ts
isPremiumActive(user)   // = is_premium === true VÀ premium_expired_at > now
Không được tin mỗi cờ is_premium Backend để is_premium = true cho tới lần quét dọn kế tiếp, kể cả khi gói đã hết hạn. Mọi chỗ hiển thị huy hiệu/quyền lợi phải so premium_expired_at với thời điểm hiện tại. Hàm trên trả về 3 trạng thái: none (chưa từng mua) · active (còn hạn) · expired (hết hạn → hiện nút gia hạn).

  • Webhook cần URL công khai — chạy ngrok http 8080 rồi khai URL ngrok vào dashboard PayOS.
  • Test deep link không cần thanh toán thật:

6. Socket.IO (Realtime)

Không cần đăng ký dịch vụ bên ngoài — server Socket.IO do backend tự vận hành. Việc cần làm ở app chỉ là trỏ đúng địa chỉ và đảm bảo hạ tầng cho WebSocket đi qua được.

6.1. Cấu hình phía app

EXPO_PUBLIC_SOCKET_URL=https://api.soundspal.com   # gốc domain, KHÔNG kèm /socket.io
EXPO_PUBLIC_SOCKET_PATH=/socket.io                # mặc định của Socket.IO
Phân biệt URL và PATH Sai lầm phổ biến: nhét luôn /socket.io vào SOCKET_URL. Khi đó client gọi tới https://host/socket.io/socket.io/ → 404 và không bao giờ kết nối được.

6.2. Yêu cầu phía hạ tầng

Hạng mục Cần làm gì
Nginx / reverse proxy Phải cho phép nâng cấp giao thức, nếu không WebSocket bị hạ xuống polling (hoặc chết hẳn): 
location /socket.io/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
}
Load balancer nhiều instance Bật sticky session, hoặc dùng socket.io-redis-adapter. Không thì mỗi lần polling rơi vào node khác → mất session
Xác thực Client gửi token ở 3 chỗ (auth.token, query.token, header Authorization) — backend đọc chỗ nào cũng được. Lưu ý extraHeaders chỉ có tác dụng ở transport polling, WebSocket thuần không gửi header tuỳ ý
Theo dõi presence Server phải coi user là offline khi socket ngắt, vì đó là điều kiện để messaging-service quyết định có gửi push hay không

6.3. Hợp đồng sự kiện

Danh sách đầy đủ ở tài liệu kiến trúc và tài liệu Messaging. Hai điểm backend cần biết:

  • Sự kiện message:read đang được gửi ở hai dạng payload khác nhau (gateway gửi {messageId, userId}, REST gửi {messageId, readerId, conversationId}). App đã chuẩn hoá cả hai, nhưng thống nhất lại một dạng thì sạch hơn.
  • App đã wire sẵn users:online (snapshot toàn bộ người đang online lúc kết nối) nhưng backend hiện chưa phát sự kiện này. Khi backend bật, presence sẽ tự khởi tạo đúng ngay từ lúc kết nối mà không cần sửa app.

6.4. Debug khi socket không kết nối

Triệu chứng trong log Khả năng cao là
❌ Socket connection error: xhr poll error Sai URL/PATH, hoặc server không chạy, hoặc CORS chặn
⚠️ Cannot connect: user not authenticated Chưa đăng nhập — SocketProvider chỉ kết nối khi có userId và accessToken
Reason: io server disconnect Server chủ động đá ra — thường do token hết hạn hoặc không hợp lệ
❌ Max reconnection attempts reached Đã thử 5 lần với backoff. Service đặt cờ ngừng hẳn — phải khởi động lại app (hoặc đăng xuất/đăng nhập) mới thử lại
Kết nối OK nhưng không nhận được tin nhắn Chưa conversation:join đúng phòng, hoặc backend emit sai tên sự kiện (phải là message:new kiểu hai chấm)

7. EAS Build (Expo Application Services)

  1. Tạo tài khoản Expo & đăng nhập 
    npm install -g eas-cli
eas login
eas whoami
    Gói Free đủ để build, chỉ phải xếp hàng lâu hơn.
  2. Liên kết project app.json đã có sẵn extra.eas.projectId. Nếu bạn fork sang tài khoản Expo khác thì chạy eas init để sinh id mới.
  3. Hiểu 3 profile trong eas.json
    Profile Cấu hình Dùng khi
    development developmentClient: true, distribution: internal Lập trình hằng ngày — có Metro, hot reload, và có native module
    preview distribution: internal APK gửi tester cài trực tiếp
    production autoIncrement: true Sinh .aab để lên Play Store. Tự tăng versionCode ở phía Expo
  4. Để EAS quản lý keystore Lần build production đầu tiên, EAS hỏi có tạo keystore không → chọn Yes. Nó lưu an toàn trên server Expo.
    Sao lưu keystore ngay: eas credentials → Android → download. Mất keystore = không bao giờ update được app đã phát hành nữa (trừ khi đã bật Play App Signing và làm thủ tục reset key với Google).
  5. Tạo EXPO_TOKEN cho CI expo.dev → Account settings → Access tokens → Create token. Chép giá trị (chỉ hiện một lần) — sẽ dùng làm GitHub secret ở mục 8.3.
  6. Build thử tại chỗ 
    npm run build:android:dev      # development build để lập trình
npm run build:android:prod     # .aab production
.easignore có nhiệm vụ riêng EAS dùng file này thay cho .gitignore khi đóng gói source gửi lên build server. Khác biệt duy nhất: nó không loại google-services.json, để prebuild/gradle trên máy build vẫn có file cấu hình Firebase.

8. Google Play Console + Fastlane (Auto deploy)

Đích đến: push một git tag → app tự động lên Google Play track internal. Chuỗi mắt xích gồm 4 phần.

8.1. Tài khoản Google Play Developer

  1. Đăng ký & trả phí play.google.com/console — phí 25 USD, trả một lần, vĩnh viễn (không phải thuê hàng năm). Cần thẻ quốc tế.
  2. Xác minh danh tính Google yêu cầu giấy tờ tuỳ thân (và giấy tờ doanh nghiệp nếu đăng ký dạng tổ chức). Duyệt mất vài ngày đến 2 tuần — làm bước này sớm, đừng để sát ngày phát hành.
  3. Tạo ứng dụng Create app → tên, ngôn ngữ mặc định, App/Game, Free/Paid.
  4. Upload bản .aab đầu tiên BẰNG TAY
    Bắt buộc. Google Play API không cho phép tạo bản phát hành đầu tiên của một app. Fastlane sẽ báo lỗi "Package not found" nếu bạn chạy nó trước khi có ít nhất một bản upload thủ công.
    Chạy npm run build:android:prod, tải .aab về, rồi Release → Testing → Internal testing → Create new release → upload.
  5. Hoàn tất các khai báo bắt buộc Play Console bắt điền trước khi cho phát hành: Privacy policy (URL công khai), Data safety, Content rating, Target audience, Ads declaration, App access (cấp tài khoản test cho Google nếu app cần đăng nhập).

8.2. Service account — chìa khoá để CI upload

Fastlane cần một "tài khoản máy" có quyền upload. Tài khoản đó tạo trên Google Cloud, rồi cấp quyền bên Play Console.

  1. Bật Google Play Android Developer API Google Cloud Console → chọn project → APIs & Services → Library → tìm Google Play Android Developer API → Enable.
  2. Tạo service account IAM & Admin → Service Accounts → Create service account. Đặt tên vd fastlane-publisher. Phần "Grant this service account access to project" có thể bỏ qua — quyền thật sẽ cấp bên Play Console.
  3. Tạo khoá JSON Bấm vào service account vừa tạo → tab Keys → Add key → Create new key → chọn JSON → tải về.
    File JSON này cho phép phát hành app dưới tên bạn. Không commit, không đưa vào .env. Nếu lỡ lộ: xoá key ngay trong Cloud Console và tạo key mới.
  4. Mời service account vào Play Console Play Console → Users and permissions → Invite new users. Dán email của service account (dạng fastlane-publisher@<project>.iam.gserviceaccount.com, có trong file JSON ở trường client_email).

    Cấp quyền tối thiểu, chọn app cụ thể chứ đừng cấp toàn tài khoản:
    • Release to testing tracks — bắt buộc
    • View app information — bắt buộc
    • Release to production — chỉ khi muốn CI đẩy thẳng lên production
  5. Kiểm tra khoá hoạt động 
    fastlane run validate_play_store_json_key json_key:/duong/dan/key.json
    Lời mời trong Play Console có thể mất vài phút đến vài giờ mới có hiệu lực — nếu lỗi quyền, chờ rồi thử lại.

8.3. GitHub Actions secrets

Repo → Settings → Secrets and variables → Actions → New repository secret. Cần 3 secret:

Tên secret Nội dung Cách tạo giá trị
EXPO_TOKEN Access token Expo expo.dev → Account settings → Access tokens (mục 7)
GOOGLE_SERVICES_JSON google-services.json mã hoá base64 base64 -i google-services.json | pbcopy (macOS) · base64 -w 0 google-services.json (Linux)
PLAY_STORE_JSON_KEY Nội dung JSON nguyên bản của service account key Mở file JSON, copy toàn bộ nội dung, dán vào ô secret. Không base64 — Fastfile truyền thẳng vào json_key_data
CODECOV_TOKEN (tuỳ chọn) token Codecov Chỉ để upload coverage. Workflow đã đặt fail_ci_if_error: false nên thiếu cũng không sao
Chú ý khác biệt định dạng GOOGLE_SERVICES_JSON phải base64 (workflow chạy base64 -d), còn PLAY_STORE_JSON_KEY phải là JSON thô. Nhầm hai cái này là lỗi rất hay gặp.

8.4. Cài Fastlane & hiểu 4 lane

# macOS
brew install fastlane
# hoặc qua RubyGems (mọi hệ điều hành)
gem install fastlane
Lane Chạy ở Làm gì
fastlane android doctor Máy dev Kiểm tra eas --version và node -v
fastlane android bump_version Máy dev npm version patch → chạy scripts/sync-version.js để chép version sang app.json và +1 vào android.versionCode
fastlane android trigger_release Máy dev Lệnh "khai hoả". Gọi bump_version, commit chore(release): bump version to vX.Y.Z, tạo tag release-vX.Y.Z, push cả branch lẫn tag
fastlane android upload_to_playstore CI Upload ./app-release.aab lên track internal, đọc khoá từ biến môi trường PLAY_STORE_JSON_KEY, bỏ qua metadata & ảnh

8.5. Quy trình phát hành đầy đủ

Đây là toàn bộ chuỗi tự động, từ một lệnh trên máy bạn đến app trên Play Store:

  1. Bạn gõ một lệnh duy nhất 
    fastlane android trigger_release
  2. Fastlane tăng version và push tag 1.0.28 → 1.0.29, versionCode 13 → 14, tạo và push tag release-v1.0.29.
  3. GitHub Actions bắt được tag Workflow eas-build.yml kích hoạt bởi on: push: tags: ['release-v*'].
  4. CI khôi phục google-services.json Giải mã secret base64 ra file. Nếu thiếu secret, job dừng ngay với thông báo tiếng Việt chỉ rõ cần thêm secret nào.
  5. EAS build production 
    eas build --platform android --profile production --non-interactive --wait --json > eas-build.json
    Cờ --json đẩy log thường sang stderr nên stdout chỉ còn JSON sạch. --wait khiến job chờ build xong (thường 10–25 phút).
  6. Tải file .aab về 
    URL=$(jq -er '.[0].artifacts.applicationArchiveUrl' eas-build.json)
curl -fSL -o ./app-release.aab -H "Authorization: Bearer ${EXPO_TOKEN}" "$URL"
    Vì sao không dùng eas build:download? Lệnh đó không hỗ trợ --latest/--output cho AAB dạng store, nên workflow lấy URL trực tiếp từ JSON.
  7. Fastlane upload lên Play Store Cài Ruby 3.2 + fastlane, chạy lane upload_to_playstore với PLAY_STORE_JSON_KEY.
  8. Bạn duyệt phát hành trên Play Console Bản build nằm ở track Internal testing. Muốn ra ngoài thì Promote release lên Closed/Open testing rồi Production.

8.6. Lỗi hay gặp khi deploy

Lỗi Nguyên nhân Cách xử lý
Package not found: com.jonasaugust12.talent_link Chưa từng upload bản nào bằng tay Làm bước 4 của mục 8.1
APK specifies a version code that has already been used versionCode trùng bản đã có Chạy lại bump_version. Lưu ý cả sync-version.js và autoIncrement của EAS đều tăng số này — có thể nhảy cách quãng, không sao
The caller does not have permission Service account chưa được cấp quyền, hoặc lời mời chưa hiệu lực Kiểm tra Users and permissions; chờ vài phút; xác nhận client_email đúng
Google Api Error: applicationNotFound package_name trong Appfile khác Play Console Đối chiếu với app.json → android.package
EAS build fail: google-services.json is missing Thiếu secret, hoặc base64 sai (thừa xuống dòng) Tạo lại bằng base64 -w 0 (Linux) để ra một dòng duy nhất
App cài được nhưng không gọi được API Build trên CI không có file .env Vấn đề cần lưu ý của repo hiện tại — xem cảnh báo ngay dưới
Khoảng trống trong pipeline hiện tại: biến môi trường lúc build CI .env nằm trong .gitignore và .easignore, nên bản build từ GitHub Actions không có 7 biến EXPO_PUBLIC_*. App sẽ cài được nhưng không kết nối được backend.

Ba cách xử lý, chọn một:
  • EAS Environment Variables (khuyến nghị): khai báo trên expo.dev → Project → Environment variables cho môi trường production. EAS tự inject lúc build, không cần đụng workflow.
  • env trong eas.json: thêm khối "env": { ... } vào profile production. Đơn giản nhưng giá trị bị commit vào repo.
  • Ghi .env từ GitHub secret: thêm một step trước eas build để tạo file, và bỏ .env khỏi .easignore.
