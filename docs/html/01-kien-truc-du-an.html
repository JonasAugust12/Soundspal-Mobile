Kiến trúc dự án

Toàn bộ cấu trúc thư mục, vai trò của từng file, và — quan trọng nhất — dữ liệu đi như thế nào từ lúc người dùng chạm màn hình cho tới khi về lại giao diện. Đọc xong tài liệu này bạn sẽ biết chính xác cần mở file nào khi muốn sửa một thứ bất kỳ.

1. Bức tranh 60 giây

Soundspal (tên repo cũ: TL-Mobile / talent_link) là ứng dụng di động React Native + Expo kết nối ba nhóm người dùng trong ngành âm nhạc:

Vai trò (role) Là ai Dùng app để làm gì
singer Ca sĩ / nghệ sĩ biểu diễn Tạo hồ sơ, ứng tuyển gig, thu âm challenge, nhắn tin
producer Nhà sản xuất / beatmaker Đăng beat, tạo challenge, nhận cộng tác
venue Quán bar / phòng trà / sự kiện Đăng tin tuyển, duyệt hồ sơ ứng tuyển, liên hệ nghệ sĩ

App không chứa business logic phía server. Nó là client gọi REST API (axios) + WebSocket (socket.io-client) tới backend microservices, và giữ 2 loại state ở local:

Thứ chỉ tồn tại ở máy người dùng: token đăng nhập, theme, bookmark, trạng thái realtime của phòng chat, bài nhạc đang phát.

2. Ba tầng của Clean Architecture

Mỗi feature trong features/ đều có đúng 3 thư mục con theo Clean Architecture. Quy tắc vàng: mũi tên phụ thuộc chỉ đi vào trong — presentation biết data, data biết domain, còn domain thì không biết gì cả.

🎨 presentation/ — Giao diện & state phía client
screens/ màn hình · components/ component con · hooks/ React Query hooks · store/ Zustand slice
Được phép import React, Expo, thư viện UI. Không gọi axios trực tiếp.
↓ gọi xuống
🔌 data/ — Nói chuyện với thế giới bên ngoài
datasources/ khai báo endpoint bằng createApiCall · repositories/ lớp cài đặt interface của domain · mappers/ đổi DTO server → entity client
Đây là nơi duy nhất được import apiClient.
↓ cài đặt / dùng type của
🧠 domain/ — TypeScript thuần, không React

Cấm import React / Expo / axios. Vì vậy tầng này test được không cần mock.
Vì sao phải chia tầng như vậy? Đổi backend từ REST sang GraphQL → chỉ sửa data/. Đổi UI từ màn hình này sang màn hình khác → chỉ sửa presentation/. Logic tính phần trăm hoàn thiện hồ sơ nằm ở domain/ nên viết unit test không cần dựng React Native.

6. Luồng khởi động app

Đây là thứ tự chính xác các việc xảy ra từ lúc bấm icon tới lúc thấy màn hình đầu tiên. Tất cả bắt nguồn từ app/_layout.tsx.

  1. Metro nạp bundle, chạy side-effect đầu tiên Dòng import '@/features/notifications/presentation/handlers/registerBackgroundHandler' trong _layout.tsx đăng ký setBackgroundMessageHandler() của Firebase. Phải sớm — RNFirebase yêu cầu handler tồn tại trước khi app khởi động xong, nếu không push lúc app bị kill sẽ không chạy.
  2. Dựng cây Provider (từ ngoài vào trong) 
    <QueryClientProvider>      // cache React Query
  <SafeAreaProvider>       // tránh tai thỏ / thanh điều hướng
    <KeyboardProvider>     // react-native-keyboard-controller
      <SocketProvider>      // vòng đời WebSocket
        <RootLayoutNav />   // nơi các hook bootstrap chạy
  3. useAuthHydration() — chờ MMKV nạp xong Zustand persist đọc key auth-storage từ MMKV. Hook này trả true khi xong. Lưu ý trong code: rehydrate thường đồng bộ và có thể xong trước khi ta kịp subscribe, nên hook phải kiểm tra hasHydrated() ngay trong effect — nếu không app kẹt màn loading vĩnh viễn.
  4. useAuthInitialize() — xác thực token với server Nếu có accessToken → gọi GET /users/me để làm mới thông tin user (is_verified, avatar_url, tier… có thể đã đổi từ web). Có guard mức module (initPromise) đảm bảo chỉ gọi một lần mỗi lần mở app dù hook được gọi từ nhiều nơi. Nếu token hỏng, interceptor 401 sẽ tự lo (refresh → thất bại → logout).
  5. useProtectedRoute() — quyết định đi đâu Chạy 3 luật guard ở mục 5. Đây là lý do bạn không thấy code router.replace('/login') rải rác trong các màn hình — tất cả tập trung một chỗ.
  6. Đăng ký push notification usePushNotifications() gắn 3 listener FCM (foreground / tap khi background / tap khi app đã bị kill). usePushTokenSync() lắng nghe onTokenRefresh để đẩy token mới lên POST /auth/device-token.
  7. Đồng bộ theme & render useThemeStore → setColorScheme() của NativeWind, rồi render <Stack> chứa 11 route group + <AppDialogHost> + <Toast>.

  1. Màn hình gọi hook, không quan tâm cách lấy dữ liệu 
    const { data, isLoading, error } = useGetJobs(filters);
  2. Hook React Query khai báo cache Hook định nghĩa queryKey (định danh cache) và queryFn (cách lấy). Nhờ queryKey, hai màn hình cùng hỏi một dữ liệu sẽ dùng chung một lần gọi mạng. Mọi feature đều gom key vào một object như jobKeys, messagingKeys, paymentKeys.
  3. Repository — điểm nối giữa domain và data Lớp *RepositoryImpl implements interface I*Repository của domain. Trong dự án này nó thường chỉ gán thẳng hàm từ datasource — nhưng chính chỗ này cho phép sau này thêm cache offline hay đổi nguồn dữ liệu mà màn hình không phải sửa dòng nào.
  4. Datasource — khai báo endpoint Toàn bộ URL của một feature nằm gọn trong một file: 
    export const authRemoteDataSource = {
    login:  createApiCall<LoginResponse, LoginRequest>('POST', '/auth/login'),
    getMe:  createApiCall<GetMeResponse>('GET', '/users/me'),
};
    Muốn biết app gọi những API nào? Đọc các file *RemoteDataSource.ts là đủ.
  5. createApiCall chuẩn hoá request Tự chọn params cho GET / data cho method khác; tự đặt Content-Type: application/json — trừ khi body là FormData (khi đó phải để axios tự sinh boundary); log 📡 → ✅/❌ ra console.
  6. Interceptor gắn token, gửi đi, trả về Response đi ngược lên. React Query lưu vào cache theo queryKey, màn hình re-render với data. Lần sau vào lại trong 5 phút → trả cache tức thì, không gọi mạng.

8. Luồng dữ liệu: GHI (mutation) & cơ chế refresh token

Ghi dữ liệu dùng useMutation thay useQuery. Điểm khác biệt quan trọng là invalidate: sau khi ghi thành công phải báo cho React Query biết cache nào đã cũ. 

export const useDeleteBeat = () => {
    const queryClient = useQueryClient();
    return useMutation({
        mutationFn: (id: string) => challengeRepository.deleteBeat(id),
        onSuccess: () => {
            // Xoá beat → danh sách beat của tôi VÀ danh sách beat chung đều cũ
            queryClient.invalidateQueries({ queryKey: ['my-beats'] });
            queryClient.invalidateQueries({ queryKey: ['beats'] });
        },
    });
};
Messaging là ngoại lệ có chủ ý Tin nhắn không đi qua React Query. Nguồn sự thật là messagingStore (Zustand) để socket đẩy tin nhắn/typing/online vào thẳng store — thêm cache thứ hai sẽ khiến refetchOnMount ghi đè mất tin socket vừa đẩy về. Xem useConversationMessages.ts.

Vòng đời token & hàng đợi 401

Đây là đoạn logic tinh vi nhất trong apiClient.ts. Vấn đề: khi token hết hạn, nếu 5 request cùng nhận 401 thì sẽ có 5 lần gọi refresh song song → server có thể thu hồi refresh token → user bị đá ra oan.

  1. Request bất kỳ nhận về 401 Interceptor kiểm tra cờ _retry để không lặp vô hạn.
  2. Nếu đang có ai đó refresh rồi (isRefreshing = true) Request này không gọi refresh nữa mà đẩy resolve/reject của mình vào failedQueue và chờ.
  3. Request đầu tiên đứng ra refresh Gọi POST tới EXPO_PUBLIC_AUTH_REFRESH_URL bằng axios trần (không qua apiClient, tránh interceptor tự gọi lại chính nó) với body { refresh_token }.
  4. Thành công → giải phóng hàng đợi Giải mã token mới bằng getUserFromToken(), lưu vào authStore, gọi processQueue(null, access_token) để mọi request đang chờ được retry với token mới.
  5. Thất bại → đăng xuất sạch processQueue(error) reject tất cả, gọi logout(). Store rỗng → useProtectedRoute phát hiện → đá về màn login.
Ngoại lệ: request multipart không retry được FormData bị "tiêu thụ" sau lần gửi đầu tiên. Retry nó sẽ gửi body rỗng và báo lỗi khó hiểu ERR_NETWORK. Vì vậy apiClient kiểm tra isFormDataBody() và chủ động reject với mã ERR_UPLOAD_AUTH_REFRESH kèm thông báo "hãy thử lại", thay vì retry mù.

Quy tắc sống còn: socket sống = không có push notification Messaging-service chỉ gửi push cho người offline. Vì vậy SocketProvider lắng nghe AppState và chủ động disconnect() khi vào background, kết nối lại khi trở lại active.
