Blog & Bình luận

Đọc và viết bài, bình luận có phân cấp, lưu bài. Đáng chú ý về mặt kỹ thuật: đây là feature phải chịu đựng nhiều biến thể response nhất từ backend, và có luồng tạo bài 4 bước chứ không phải một request.

1. Tổng quan

Route Màn hình
(blog)/index BlogIndexScreen — danh sách, tab, tìm kiếm
(blog)/[id] BlogDetailScreen — đọc bài + bình luận
Không có endpoint GET /blogs/{id} Backend không cung cấp API lấy chi tiết một bài. useBlogArticle(id) phải lách: nó fetchQuery toàn bộ feed rồi .find(p => p.id === articleId).

Hệ quả trực tiếp: bài nào không nằm trong trang feed đầu tiên thì mở chi tiết sẽ báo "Blog not found" — kể cả khi bài đó tồn tại. Deep link tới bài cũ cũng gãy vì lý do này.

2. Endpoint

Method Path Ghi chú
GET /blogs Feed. Params: topic_id, author_id, page_size, page
GET /blogs/topics Danh sách chủ đề (sinh ra các tab)
GET /blogs/search?q=… Query string dựng tay, hỗ trợ tag_ids[] lặp lại
POST /blogs Tạo bài: {title, content, short_description, topic_id, tags[]}
PUT /blogs/{id} Sửa bài (cùng body)
PATCH /blogs/{id}/publish Xuất bản — không có body
POST /storage/upload Upload ảnh bìa (multipart, field file)
POST /blogs/{postId}/media Gắn URL ảnh vào bài: {url, media_type, embed_id?}, timeout 60 giây
GET /bookmarks Bài đã lưu
POST / DELETE /blogs/{postId}/bookmark Lưu / bỏ lưu
GET /blogs/{postId}/comments Danh sách bình luận
POST /blogs/{postId}/comments {content, parent_id?}
PUT / DELETE /comments/{commentId} Sửa / xoá bình luận
GET /users/{id} Gọi phụ để bổ sung thông tin tác giả bình luận (xem mục 7)

Không tồn tại: xoá bài viết, thích bài, thích bình luận. Ba thứ này không có endpoint nào.

3. Mô hình dữ liệu

Có hai kiểu cần phân biệt: BlogItem là dữ liệu thô từ server, còn BlogPost là kiểu client dùng sau khi qua mapper.

BlogItem (server)

{
    id, author_id, topic_id, title, slug,
    status: 'draft' | 'published' | 'archived',
    short_description, content,
    read_time, view_count, upvote_count, downvote_count,
    comment_count, bookmark_count,
    published_at, created_at, updated_at,
    tags: string[],
    media: BlogMedia[]     // { id, url, media_type, embed_id? }
}

BlogComment (client)

{
    id, author: { id, name, avatar },
    text?, timestamp,        // timestamp đã format sẵn: "5m ago"
    likes: number,
    parentId?: string | null,
    voiceUrl?, voiceDuration?, isVoiceMessage?   // xem mục 8
}

4. Hook & cache

Hook Query key staleTime
useBlogTopics ['blogTopics'] 30 phút (chủ đề ít đổi)
useBlogFeed ['blogPosts','feed'] 5 phút
useBlogSearch ['blogSearch', q, topic_id, sort, tag_ids] 0 — có placeholderData giữ kết quả cũ trong lúc tải mới
useBookmarksList ['bookmarks','list'] 2 phút
useBlogComments ['blogComments', postId] 0
useBlogArticle ['blogArticle', id] 30 phút
Không có infinite query nào trong feature này useInfiniteQuery không xuất hiện ở đâu. Tham số phân trang (limit, offset, page) có trong datasource nhưng không caller nào truyền — useBlogPosts (hook nhận filters) là code chết, không nơi nào gọi.

5. Danh sách & tìm kiếm

Tab được ghép từ hai nguồn:

Tab Nguồn Lọc thế nào
Dành cho bạn (for-you) useBlogFeed() Toàn bộ feed
Bài viết của tôi Cùng feed Lọc client author_id === user.id
Đã lưu blogBookmarkStore (MMKV) Đọc thẳng từ store
Tab chủ đề (động) Cùng feed Lọc client topic_id === activeTab
Chỉ có MỘT lần gọi feed cho tất cả tab Mọi tab không phải tìm kiếm đều lọc phía client trên cùng mảng listPosts. Nghĩa là "Bài viết của tôi" chỉ thấy bài của bạn nằm trong trang feed đầu. Bài cũ hơn sẽ không xuất hiện.

Tìm kiếm là kiểu submit, không phải gõ tới đâu tìm tới đó:

  • searchDraft giữ ký tự đang gõ; onSubmitEditing mới chép sang committedSearch.
  • Xoá trắng ô tìm kiếm thì thoát chế độ tìm ngay lập tức.
  • Chỉ tham số q được gửi. topic_id, sort, tag_ids có trong kiểu dữ liệu nhưng giao diện không bao giờ điền.

Tab "Bài viết của tôi" và "Đã lưu" yêu cầu đăng nhập — chưa đăng nhập thì hiện màn "Đăng nhập để…" và query tìm kiếm cũng bị tắt.

Vì sao ô tìm kiếm nằm ngoài FlatList? Comment trong code ghi rõ: đặt TextInput bên trong FlatList khiến bàn phím đóng lại sau mỗi ký tự. Nên chỉ có bài nổi bật là ListHeaderComponent, còn ô tìm kiếm và thanh tab nằm bên ngoài.

6. Đọc bài viết

Màn chi tiết gồm các phần theo thứ tự:

  1. Ngày xuất bản, tiêu đề, khối tác giả (xem mục 7)
  2. Ảnh bìa
  3. Nội dung HTML render bằng react-native-render-html, có bảng tagsStyles riêng cho body/p/h1/h2/h3/ul/ol/li/strong/a/blockquote, hỗ trợ dark mode, và selectable: true
  4. Một khối trích dẫn — ghép cứng từ tiêu đề bài, không phải nội dung thật
  5. Hàng thống kê: view_count / comment_count / upvote_count
  6. Chip thẻ
  7. Bài liên quan: lấy 3 bài đầu trong feed khác bài hiện tại — không có logic liên quan thật
Chống trùng tiêu đề stripOpeningH1IfMatchesTitle() gỡ thẻ <h1> đầu tiên của HTML nếu nội dung nó trùng article.title — nếu không, tiêu đề bị hiển thị hai lần. Hàm so sánh có giải mã &nbsp; &amp; &lt; &gt; và lột thẻ trước khi đối chiếu.

7. Hiển thị tác giả

useBlogAuthorDisplay(authorId) có một quy tắc thương hiệu:

const realName = (user?.display_name || user?.username || '').trim();
const isSoundspal = realName === '' || realName === 'System Administrator';

return {
    name: isSoundspal ? 'SoundSpal' : realName,
    avatarUrl: isSoundspal ? undefined : user?.avatar_url,   // → dùng logo app
    isSoundspal,
};

Bài do tài khoản hệ thống viết được gắn thương hiệu "SoundSpal" + logo app. Người thật thì hiện tên và avatar của họ.

Trong lúc tải, hook cố tình báo isSoundspal: true Tên rỗng lúc đang tải cũng cho ra isSoundspal = true. Chủ ý: tránh nháy chữ "Tác giả" mặc định rồi mới đổi thành tên thật.

Bổ sung thông tin tác giả bình luận

Bình luận từ server thường chỉ có author_id, không có tên và avatar. Datasource xử lý bằng enrichCommentAuthors():

  1. Gom danh sách id tác giả duy nhất
  2. Gọi song song GET /users/{id} Dùng Promise.all, mỗi lời gọi .catch(() => null) để một id hỏng không làm hỏng cả danh sách.
  3. Ghi ngược vào dữ liệu thô rồi mới map Điền author_username / author_avatar_url vào từng dòng.

8. Bình luận

Phân cấp tối đa 2 tầng

rootIdOf() lần ngược chuỗi parentId để tìm gốc, rồi dựng danh sách phẳng {comment, isReply}: mỗi bình luận gốc theo sau là các trả lời của nó. Dữ liệu cũ có lồng sâu hơn cũng bị ép về 2 tầng. Nút "Trả lời" bị ẩn trên các trả lời — nên chỉ trả lời được bình luận gốc.

Vòng lặp lần ngược có chặn trên 10 vòng để sống sót nếu dữ liệu có parentId vòng tròn.

Ghi thẳng vào cache thay vì refetch

Cả ba mutation (tạo/sửa/xoá bình luận) đều setQueryData trực tiếp vào ['blogComments', postId].

Vì sao không dùng invalidate cho gọn? Comment trong code ghi: refetch chạy đua với thời điểm backend commit — bình luận mới không hiện cho tới khi người dùng tự tải lại trang. Ghi thẳng vào cache giải quyết triệt để.

Kèm theo đó là hai vá lỗi nhỏ: (1) nếu response thiếu parent_id thì chép từ request để trả lời lồng đúng ngay; (2) response thường thiếu tên/avatar người gửi nên code lấy từ authStore điền vào — nếu không, bình luận vừa gửi hiện là "User" với avatar mặc định.

Bình luận giọng nói — giao diện rỗng, chưa có gì phía sau

Tính năng này chưa được cài đặt Nếu bạn thấy VoiceCommentButton, VoicePlayer và các trường voiceUrl/voiceDuration mà tưởng đã có bình luận giọng nói — chưa có. Cụ thể:
  • VoiceCommentButton chỉ là nút hiển thị, không có code ghi âm, và không được import ở đâu cả.
  • VoicePlayer không dùng thư viện âm thanh nào. Nút play chỉ đổi state cục bộ. Dạng sóng là 20 thanh sinh bằng Math.sin(i * 0.5) — hoàn toàn trang trí.
  • mapApiCommentToBlogComment hardcode isVoiceMessage: false, nên VoicePlayer không bao giờ được render từ dữ liệu server.
  • BlogDetailScreen truyền allowVoice={false} → nút micro bị ẩn hoàn toàn.
  • expo-av có trong dependency nhưng feature blog không import nó (chỉ challenge và profiles dùng).

9. Tạo bài viết — luồng 4 bước

Đây không phải một request. Tạo một bài có ảnh bìa cần 4 lần gọi mạng:

1. Tạo bàiPOST /blogs
→
2. Upload ảnhPOST /storage/upload
→
3. Gắn mediaPOST /blogs/{id}/media
→
4. Xuất bảnPATCH /blogs/{id}/publish

Điều kiện hợp lệ

Trường Luật
Tiêu đề ≥ 3 ký tự
Nội dung ≥ 20 ký tự
Chủ đề Bắt buộc chọn
Thẻ Ít nhất 1, tối đa 5 — chọn từ danh sách 12 thẻ hardcode
Mô tả ngắn ≤ 200 ký tự; bỏ trống thì tự lấy content.slice(0, 200)
Bài được tạo sớm nếu chọn ảnh trước Nếu người dùng chọn ảnh bìa trước khi bấm gửi, code tạo bài ngay lập tức để có postId mà gắn media, rồi lưu id đó vào draftPostId. Khi bấm gửi, nó bỏ qua bước tạo. Nhờ vậy không bao giờ có ảnh mồ côi không thuộc bài nào.

Sửa & xoá

  • Nút "Sửa" (biểu tượng bút chì) chỉ hiện ở tab "Bài viết của tôi".
  • EditBlogModal sửa được tiêu đề, nội dung, mô tả ngắn, chủ đề, thẻ. Không đổi được ảnh bìa — ảnh cũ chỉ hiện ở dạng chỉ đọc.
  • Xoá bài viết không tồn tại — không có endpoint, không có hook, không có nút.
Ngôn ngữ không nhất quán CreateBlogModal dùng tiếng Việt, còn EditBlogModal dùng tiếng Anh ("Edit blog post", "Save changes", "Title must be at least…"). Nhãn thời gian bình luận cũng là tiếng Anh (5m ago, 2d ago) trong một khung bình luận tiếng Việt. Đáng dọn lại.

10. Upload ảnh — bản sao riêng của blog

Blog KHÔNG dùng helper chung postMultipartWithFetch Nó có bản sao riêng: postStorageUploadWithFetch() trong data/utils/blogMediaUtils.ts. Chức năng gần như giống hệt, nhưng là code riêng — sửa helper chung không ảnh hưởng tới blog.

Chi tiết đường upload:

  1. Chuẩn hoá tên file và MIME MIME mặc định image/jpeg. Tên file chỉ giữ nếu đã có phần mở rộng, ngược lại sinh cover_{timestamp}.{ext}.
  2. Gửi bằng fetch Field file, header chỉ có Accept và Authorization — không đặt Content-Type để React Native tự sinh boundary. Timeout 120 giây bằng AbortController.
  3. Rút URL từ response extractStorageUploadUrl() thử lần lượt root.url → root.data.url → root.data.file_url.
  4. Gắn vào bài bằng axios POST /blogs/{postId}/media với {url, media_type}, timeout 60 giây.

Mọi bước đều log qua console.warn với tiền tố [BlogMediaUpload] và nhãn giai đoạn ([start], [step:storage], [step:attach], [done], [ERROR]) — rất hữu ích khi debug upload thất bại.

Lỗi được dịch bởi formatBlogFlowError(), có xử lý riêng cho ERR_UPLOAD_AUTH_REFRESH (token hết hạn giữa chừng upload) và ERR_NETWORK.

11. Mapper — server nói gì, client hiểu gì

mapBlogItemToBlogPost() giữ nguyên mọi trường snake_case và thêm các bí danh cho giao diện:

Trường client Lấy từ
thumbnail media[0].url
excerpt short_description
publishedAt Format vi-VN dd/mm/yyyy; ngày thiếu/sai → 'Chưa xuất bản'
likes / comments upvote_count / comment_count
category Hardcode 'BÀI VIẾT'
creator_username author_id — một id bị nhét vào trường tên username
creator_display_name Hardcode 'Tác giả'
creator_role Hardcode 'user'
Hệ quả của việc hardcode creator_role Hàm creatorRoleLabel() ánh xạ artist→"Nghệ sĩ", producer→"Nhà sản xuất", venue→"Nhà tuyển dụng". Nhưng vì mapper luôn đặt 'user', nhãn luôn hiển thị "Tác giả". Chuỗi ánh xạ kia là code chết trong thực tế.

normalizeBlogTopics() thì đặc biệt phòng thủ: bóc tới 3 lớp data lồng nhau, chấp nhận mảng trần hoặc {items|topics|data}, và chấp nhận cả chuỗi trần (tự sinh id bằng slug). Có unit test riêng — file test duy nhất của feature này.

12. Đánh dấu bài viết

Thiết kế hai nguồn: store MMKV (blog-bookmarks-v1) là nguồn hiển thị, còn API là đích đồng bộ.

  1. Bấm lưu → cập nhật store ngay (optimistic)
  2. Gọi API POST/DELETE /blogs/{postId}/bookmark.
  3. Lỗi → hoàn tác store + hiện toast "Không thể lưu bài viết" / "Không thể bỏ lưu".
mergeServer() có một chốt chặn quan trọng 
if (!serverPosts.length) return state;  // đừng ghi đè bằng rỗng
Server trả mảng rỗng (do chậm, do lỗi, do chưa đồng bộ) không được xoá sạch danh sách local. Nếu không có dòng này, bài vừa lưu sẽ biến mất ngay sau đó.

13. Chuẩn hoá response — nhiều lần vá lỗi

Backend bọc dữ liệu ở nhiều tầng khác nhau tuỳ endpoint. Feature này có hẳn một lớp hàm để chịu đựng điều đó:

Hàm Xử lý
extractArrayFromEnvelope() Bóc tới 3 tầng, chấp nhận mảng trần hoặc {items|data|posts|bookmarks|comments|records}
unwrapBlogData() Bóc {data}, ném lỗi có nhãn nếu thiếu
normalizeBlogTopics() Bóc 3 tầng + chấp nhận chuỗi trần
mapBookmarkRowToBlogPost() Dòng có post lồng thì map cái đó, không thì coi chính dòng là BlogItem

Comment trong code ghi rõ lý do: bản bóc một tầng trước đây trả về [] cho response lồng nhiều tầng, khiến bookmark và bình luận biến mất hoàn toàn dù backend có trả dữ liệu.

14. Code chết & điểm cần dọn

  • useBlogPosts — không caller nào, kéo theo mọi logic phân trang thành không thể chạm tới.
  • useAddBlogComment, useAddCommentLike — đã đánh dấu @deprecated, chỉ là hàm rỗng.
  • TagSelector.tsx — được export nhưng không ai import; cả hai modal đều tự viết lại giao diện chip thẻ, kèm hai bản sao giống hệt của danh sách 12 thẻ.
  • VoiceCommentButton — export nhưng không import.
  • BLOG_FEED_TABS — @deprecated, chỉ giữ để không vỡ import.
  • IBlogRepository thực ra là typeof blogRemoteDataSource — tức "hợp đồng domain" đang được suy ra ngược từ tầng data, trái với nguyên tắc Clean Architecture. Đây là ngoại lệ so với các feature khác.
