Thông báo đẩy (Push / FCM)

Feature nhỏ về số dòng code nhưng nhiều bẫy nhất dự án. Chỉ có 1 endpoint, 3 hook và 1 handler — nhưng mỗi phần đều đang né một hành vi khó chịu của Android, iOS hoặc chính thư viện Firebase.

1. Toàn cảnh

File Nhiệm vụ Gọi từ đâu
handlers/registerBackgroundHandler.ts Đăng ký handler nhận message khi app ở nền / đã bị kill import side-effect ở đầu app/_layout.tsx
hooks/useDevicePayload.ts Xin quyền + lấy FCM token + device_id LoginScreen, useGoogleSignIn
hooks/usePushNotifications.ts 3 listener nhận/điều hướng thông báo app/_layout.tsx
hooks/usePushTokenSync.ts Đẩy token mới lên server khi FCM xoay vòng app/_layout.tsx
domain/utils/resolvePushRoute.ts Suy màn hình đích từ data của message usePushNotifications
data/deviceInfo.ts Sinh & lưu device_id, xác định platform 2 hook trên
data/datasources/notificationRemoteDataSource.ts POST /auth/device-token usePushTokenSync
Feature này KHÔNG có màn hình nào Không có "trung tâm thông báo" trong app. Thông báo do hệ điều hành hiển thị; nhiệm vụ duy nhất của app là đăng ký nhận và điều hướng khi người dùng bấm vào. (Tab tên "notifications" trong (tabs) thực ra là danh sách chat.)

2. Ba trạng thái app — ba cách xử lý khác nhau

Đây là kiến thức nền quan trọng nhất. Cùng một message FCM, tuỳ app đang ở trạng thái nào mà hành vi khác hẳn:

Trạng thái app OS có tự hiện banner? Callback được gọi Ai xử lý trong dự án
Foreground (đang mở) Không onMessage usePushNotifications → tự hiện toast bằng showInfo()
Background (ở nền) Có setBackgroundMessageHandler registerBackgroundHandler — thân hàm để trống có chủ ý
Bấm vào thông báo (app ở nền) — onNotificationOpenedApp usePushNotifications → router.push()
Bấm vào thông báo (app đã bị kill) — getInitialNotification — onNotificationOpenedApp KHÔNG bắn usePushNotifications → router.push()
Vì sao thân background handler để trống? 
setBackgroundMessageHandler(getMessaging(getApp()), async (message) => {
    console.warn('[FCM] background message:', message?.messageId);
});
Khi message có khối notification, hệ điều hành đã tự hiện banner rồi. Nếu handler cũng hiện thêm thì người dùng thấy hai thông báo trùng nhau. Nhưng handler vẫn phải tồn tại — React Native Firebase yêu cầu nó được đăng ký, nếu không sẽ cảnh báo và message data-only bị bỏ qua.

Vì lý do đó, app/_layout.tsx import file này ở đầu file dưới dạng side-effect: handler phải sẵn sàng trước khi app khởi động xong.

3. Lấy quyền & token — nơi có bẫy lớn nhất

requestPermission() của RNFirebase KHÔNG hỏi gì trên Android Hàm này được đánh dấu @platform ios và trên Android nó chỉ return Promise.resolve(AUTHORIZED) — không hiện hộp thoại nào.

Tin vào nó thì trên Android 13+ quyền POST_NOTIFICATIONS mặc định bị từ chối. Hậu quả cực khó debug: FCM vẫn giao message (background handler vẫn chạy, log vẫn ra), nhưng hệ điều hành lặng lẽ không hiện banner. Nhìn từ ngoài giống hệt "server không gửi push".

Cách ensureNotificationPermission() xử lý:

if (Platform.OS === 'android') {
    // Dưới Android 13 (API 33): quyền được cấp sẵn lúc cài đặt
    if (Number(Platform.Version) < 33) return true;

    // Android 13+: PHẢI dùng API của React Native, không dùng RNFirebase
    const result = await PermissionsAndroid.request(
        PermissionsAndroid.PERMISSIONS.POST_NOTIFICATIONS,
    );
    return result === PermissionsAndroid.RESULTS.GRANTED;
}

// iOS: đây mới là chỗ requestPermission() thật sự làm việc
const status = await requestPermission(messaging);
return status === AuthorizationStatus.AUTHORIZED
    || status === AuthorizationStatus.PROVISIONAL;

Timeout 5 giây

getDevicePayload() bọc toàn bộ việc lấy token trong withTimeout(promise, 5000, null): 

const fcm_token = await withTimeout(requestAndGetToken(), 5000, null);
return { device_id: getOrCreateDeviceId(), fcm_token, platform: resolvePlatform() };
Nguyên tắc thiết kế: push không bao giờ được chặn đăng nhập Native call có thể treo (máy không có Play Services, mất mạng lúc đăng ký token…). Nếu đăng nhập await vô hạn thì người dùng kẹt ở màn loading. Sau 5 giây, fcm_token trả về null và người dùng vẫn đăng nhập bình thường — chỉ là tạm thời chưa nhận push. Lần đăng nhập sau, hoặc khi FCM xoay vòng token, nó sẽ tự đồng bộ lại.

device_id — định danh thiết bị ổn định

export function getOrCreateDeviceId(): string {
    const existing = storage.getString('device_id');
    if (existing) return existing;

    const id = generateUuid();   // UUID v4 tự sinh, không cần thư viện
    storage.set('device_id', id);
    return id;
}

Lưu trong MMKV nên ổn định qua mọi lần mở app. Backend dùng nó để phân biệt thiết bị: một tài khoản đăng nhập trên 3 máy = 3 device_id = 3 FCM token, và cần đẩy thông báo tới cả ba.

Hệ quả của việc lưu trong MMKV Gỡ app hoặc xoá dữ liệu app → device_id mới được sinh. Bản ghi thiết bị cũ ở backend trở thành rác. Backend nên dọn định kỳ các token mà FCM trả về UNREGISTERED.

resolvePlatform() ánh xạ Platform.OS sang giá trị backend chờ đợi: ios → 'IOS', android → 'ANDROID', còn lại 'WEB'.

4. Hai thời điểm token được gửi lên server

Khi nào Gửi qua đâu Code
Lúc đăng nhập Kèm trong body login — /auth/login hoặc /auth/mobile-oauth LoginScreen, useGoogleSignIn
Khi FCM xoay vòng token POST /auth/device-token usePushTokenSync

Body của cả hai đường đều là:

{
    device_id: string,      // UUID lưu trong MMKV
    fcm_token: string,
    platform: 'ANDROID' | 'IOS' | 'WEB'
}
Không đồng bộ token xoay vòng = push chết âm thầm FCM tự đổi token khi: cài lại app, khôi phục từ bản sao lưu, xoá dữ liệu app, hoặc định kỳ theo chính sách của Google. Token cũ ngừng hoạt động mà không có lỗi nào — server vẫn gửi, FCM vẫn nhận, chỉ là không tới máy nào cả.

Đó là lý do usePushTokenSync tồn tại. Nó chỉ lắng nghe khi isAuthenticated, và nuốt lỗi (chỉ console.warn) để không làm hỏng trải nghiệm nếu mạng chập chờn.

5. Điều hướng khi bấm thông báo

resolvePushRoute(data) là toàn bộ logic. Nó nhận khối data của message và trả về đường dẫn, hoặc null.

Thứ tự ưu tiên

  1. Suy từ type + id
    type Cần Đường dẫn
    new_application job_id /(jobs)/applicants?id={jobId}
    application_status_changed — /(jobs)/my-applications
    new_message conversation_id /(messages)/detailMessage?conversationId={id}
  2. Không có type nhưng có conversationId Vẫn mở được phòng chat — đây là trường hợp của messaging-service.
  3. Cuối cùng mới xét route / path Chỉ là phương án dự phòng.
Vì sao route chỉ là dự phòng? Comment trong code ghi rõ: messaging-service đính sẵn route: "/(messages)/<id>" — nhưng route đó không tồn tại trong app. Đường dẫn đúng phải là /(messages)/detailMessage?conversationId=<id>. Nếu tin vào route thì bấm thông báo sẽ mở màn trắng.

Hai backend, hai quy ước đặt tên

function pick(data, ...keys) {
    for (const key of keys) {
        const value = data[key];
        if (typeof value === 'string' && value.length > 0) return value;
    }
    return undefined;
}

// Thử cả hai kiểu đặt tên
const conversationId = pick(data, 'conversation_id', 'conversationId');
const jobId         = pick(data, 'job_id', 'jobId');
Service Kiểu tên Có gửi type?
job-post-service snake_case (job_id) Có
messaging-service camelCase (conversationId) Không
Có test đầy đủ resolvePushRoute và deviceInfo nằm trong số ít phần của dự án có unit test tử tế: __tests__/resolvePushRoute.test.ts, deviceInfo.test.ts, useDevicePayload.test.ts, usePushNotifications.test.ts. Logic thuần, không React → dễ test.

6. Push tin nhắn — ràng buộc với Socket

Quy tắc quan trọng nhất của cả hai feature Messaging-service chỉ gửi push cho người đang offline. "Offline" ở đây nghĩa là không có socket đang kết nối.

Vì vậy SocketProvider phải chủ động ngắt socket khi app xuống nền: 
AppState.addEventListener('change', (state) => {
    if (state === 'background') socketService.disconnect();
    else if (state === 'active') socketService.connect();
});
Không làm vậy thì người dùng không bao giờ nhận được thông báo tin nhắn — server tưởng họ vẫn đang online.

Hệ quả dây chuyền của quyết định này:

Hệ quả Cách xử lý trong code
Tin nhắn đến lúc app ở nền không về qua socket DetailMessageScreen luôn gọi lại API khi mở màn, dù đã có cache
Đang mở sẵn màn chat rồi app xuống nền và quay lại Thêm listener AppState riêng ở màn chat để fetch lại khi trở lại active
Trạng thái online của người khác bị "nhấp nháy" Chấp nhận — đây là đánh đổi có chủ ý để có push

7. Setup phía Firebase

Các bước tạo project, tải google-services.json, cấp service account cho backend và cách test được mô tả đầy đủ ở Setup bên thứ ba, mục 3. Tóm tắt những gì bắt buộc:

  • Firebase project (hiện tại: talentlink-22clc) — khác project Google Cloud dùng cho đăng nhập Google.
  • google-services.json ở thư mục gốc repo, package name phải khớp com.jonasaugust12.talent_link. File này bị gitignore, CI ghi lại từ secret base64.
  • Backend giữ service account JSON để gọi FCM HTTP v1 API.
  • app.json đã khai @react-native-firebase/app và /messaging trong plugins, cùng googleServicesFile.

8. Yêu cầu payload cho backend

Để app hoạt động đúng, message FCM nên có cả hai khối:

{
  "message": {
    "token": "<fcm_token>",
    "notification": {                 // OS dùng khối này để hiện banner
      "title": "Có người ứng tuyển mới",
      "body":  "Nguyễn Văn A vừa nộp đơn vào 'Ca sĩ acoustic tối T6'"
    },
    "data": {                         // app dùng khối này để điều hướng
      "type": "new_application",
      "job_id": "abc-123"
    }
  }
}
Thiếu khối nào Hậu quả
Thiếu notification Không có banner khi app ở nền (background handler đang cố ý để trống)
Thiếu data Bấm vào thông báo chỉ mở app ở màn cuối, không nhảy đúng chỗ
Mọi giá trị trong data phải là chuỗi FCM chỉ chấp nhận Record<string, string>. Gửi số hay boolean sẽ bị từ chối. pick() phía app cũng chỉ nhận giá trị typeof === 'string' và độ dài > 0.

10. Ghi chú & hạn chế

  • Không có lịch sử thông báo trong app. Vuốt đi là mất. Muốn có thì cần backend bổ sung endpoint và app thêm màn hình.
  • Không có cài đặt bật/tắt từng loại thông báo. settingsStore có trường notifications: boolean nhưng không được dùng ở đâu.
  • Không xoá token khi đăng xuất. logout() không gọi API huỷ đăng ký thiết bị. Thiết bị đó vẫn có thể nhận push của tài khoản cũ cho tới khi backend dọn.
  • Không có notification channel riêng cho Android. Tất cả dùng channel mặc định — không phân loại được mức độ ưu tiên.
  • Chưa cấu hình đầy đủ cho iOS. Cần APNs key trên Firebase Console và NSUserNotificationsUsageDescription; app.json hiện chưa có.
